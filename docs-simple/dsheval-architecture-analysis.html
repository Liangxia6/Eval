一句话判断

领域建模和安全边界明显强于普通 MVP，但能力覆盖、调度和真实 VM 验收仍处于单场景阶段。

最核心的设计选择 评测不相信 Agent 的最终回答，而是把行为 Trace、独立环境变化和内容摘要汇合为密封证据，再由确定性 Judge 评分。

为什么边界有效

  • 契约测试直接扫描 import，禁止业务模块相互依赖。
  • 具体实现只允许在 app/bootstrap.ts 实例化。
  • 共享模型只有一份，避免跨模块重复定义和语义漂移。

当前真实产品形态

单机 CLI + 本地文件存储 + 静态 Viewer。没有常驻 API、数据库、消息队列或分布式 Worker；运行时没有第三方生产依赖。

一次评测的真实执行链

顺序来自 runEvaluationWorkflow 的持久化节点。核心约束是：先形成可验证事实，再允许下游消费。

01

冻结输入

提交 Config、Target 描述、源码清单、锁文件与有效配置摘要。

02

检查 Target

重新校验冻结内容，确认 DSH 版本、Headless、Probe 顺序和权限事实。

03

编译计划

把 Pack 解析为单 Dataset/Case，并确定性匹配 Sensor、Judge、预算和环境能力。

04

租约与安全预检

取得单 Run 租约；验证 UID 隔离、setpriv、目录权限与网络默认拒绝。

05

准备环境与基线

创建 workspace/runtime home，暂存只读 Target，Seed 输入并采集文件 Before。

06

执行完整 Agent

使用字面 argv 启动 DSH；Probe 记录行为，文件 Sensor 独立观察副作用。

07

密封证据

Drain Probe、采集稳定 After，形成 Raw Observation、Evidence Bundle 与 Closure。

08

逐项判定

Judge 只能读取 Closure 授权的证据，输出 Finding、Judgement 和 CheckResult。

09

Reset 与验证

重置后重新独立采集；MATCH 才清理，否则隔离环境，但不改写 Agent Verdict。

10

Gate 与交付

重读已提交 CheckResult，形成唯一 Gate；JSON 为权威，HTML 与导出为派生交付。

两个容易误读的顺序 Reset 在 Gate 前完成，但 Gate 输入仍只有 CheckResult；报告在 Gate 后生成，所以报告失败不会改变已经形成的评分。

状态机不是日志装饰

Run、Case、Attempt、Environment、ObservationSession 都是带 revision 的投影。每次迁移通过 CAS 保存历史与当前版本；非法跳转、旧 revision、缺失历史或损坏摘要会阻断恢复。

模块职责与代码重心

边界清晰，但复杂度集中在少数超大文件；这不会破坏依赖方向，却会提高变更和评审成本。

可扩展的位置

  • packs/ 声明 Dataset、Scenario、Metric、Judge 绑定、环境和证据要求。
  • SensorAdapterDescriptor 绑定观测实现及能力摘要。
  • JudgeImplementation 注册实际评分算法。

扩展的真实代价

“新增 Pack 不修改源码”只适用于复用现有文件 Sensor 和规则 Judge。新增能力类型仍需同步修改实现、bootstrap 注册、Pack、证据契约和测试。

因此它是有明确扩展缝隙的单体，还不是运行时动态发现的插件平台。

证据模型与安全边界

最有价值的设计是将“Agent 做了什么”和“环境真正发生了什么”建模为不同可信等级的来源。

Cooperative Trace

DSH Probe：会话、工具调用、结果和最终回答。

→

Evidence Closure

按 Check 限制事实类型、来源、信任级别和时间边界。

→

Deterministic Judge

只读授权证据，输出 Finding、Judgement 和 CheckResult。

↑

Independent Observation

文件 Before / After / Post-reset、类型、大小、SHA-256、稳定窗口和 symlink 边界。

完整性机制

  • Canonical JSON 和 Artifact 原始字节分别计算 SHA-256。
  • 不可变对象使用摘要 Ref，生命周期对象额外绑定 revision。
  • Repository 写入时验证 Scope、Ref、提交顺序和 Gate 唯一性。
  • report.json 是权威事实，HTML 只负责展示。

运行隔离

  • 生产模式要求 Linux VM 和 dsheval/dshagent 两个 UID。
  • setpriv 清理附加组、能力并启用 no-new-privs。
  • Target 只接收受限环境变量和明确允许的目录。
  • 网络通过允许端点与禁止目标的正反探针验证默认拒绝。
  • Viewer 只能监听 loopback，并拒绝 symlink 路径。
安全保证的适用范围 Fixture 模式只返回 PROCESS_FIXTURE，不能证明生产隔离。真实安全结论必须来自 Linux VM 预检，而当前仓库仍缺这条发布验收证据。

成熟度判断与演进路线

应先补齐可重复验证的交付链，再扩展能力和规模；否则容易把可信纵向切片扩成不可验证的平台。

已经扎实

  • 模块依赖方向有自动化架构测试。
  • 双通道取证避免只相信 Agent 自述。
  • 摘要、作用域、Ref 和状态历史可发现篡改。
  • Verdict、OperationalHealth 和失败归因相互独立。
  • 生产安全预检采用 fail-closed。
  • Pack 与框架源码分离。

仍是 MVP

  • 单 VM、单 Run、单 Dataset、单 Case、单 Attempt。
  • 只有一个 Attention + PyTorch Pack。
  • 绑定 DSH 0.1.1-rc.2 和 Linux setpriv。
  • 只有文件 Sensor 与规则 Judge。
  • 没有真实 DSH + 模型 VM 发布验收。
  • Sensor/Judge 仍由 bootstrap 静态注册。
