# DSH Studio 总体开发与协作基线

> 版本：V0.1 · 合并评审稿  
> 日期：2026-09-12  
> 适用：RCA、DOA、TSA、EVA、LGA、DSHEval、DSH 运行底座及企业业务 Agent。  
> 目标：支撑一个企业项目可靠完成“需求—数据—构建—评测—批准—运行”，让下一个项目复用相同的连接方式。  
> 状态：本文提出统一开发基线，不表示相关公共服务、数据库或接口已经实现。

## 1. 评审结论与统一边界

两份原稿的主要方向可以保留：模块分工、单一权威数据源、企业隔离、版本追溯，以及评测、项目评审和真人批准分开管理。

当前主要问题是：要求清单多，能够直接联调的契约少；部分名称和责任存在冲突；存储布局容易被误读为首期建设清单。建议将原有 22 项要求收敛为本文的公共对象、模块交接、版本闭环、数据存储及开发实施五个方面。

| 处理结论 | 内容 |
|---|---|
| 直接保留 | 每类数据一个维护方；企业作用域；公开与私有数据分开；任务与尝试分开；外部动作幂等；历史证据不覆盖 |
| 修改或补齐 | 字段命名、运行 ID 语义、项目主档归属、任务接收与取消、动态数据追溯、候选版本与发布关系、正式接口样例 |
| 首期建设 | 企业/项目身份与授权、少量公共契约、持久化任务交接、受控文件访问、版本与评测关联、批准与发布检查 |
| 简化或推迟 | 逐模块微服务、先建三套数据库、全面迁移 DSHEval、全功能资源市场、数字人平台、统一模型记忆、复杂成本平台、通用流程引擎 |

**必须统一的是项目边界上的含义和行为。** 内部语言、类结构、数据库表名、框架及实现方式可以不同。公共能力可以先放在一个模块化后端中，由同一工程师负责多个区域；表中的“服务”不意味着必须独立部署。

**本次验证范围：** 已阅读两份原稿和 DSHEval 开发约定，并核对 VM 中 DSHEval 的 All Trace、Judge、评分结果和报告类型。未全面审计其他模块、DSH 内核、数据库现状和企业部署；没有执行两个企业场景的联调。下文标为“拟定”的 Studio 接口及存储安排均需实施验证，不能据此宣称已具备上线能力。

## 2. 架构与权威数据归属

### 2.1 职责与交接

| 模块 | 核心职责与输入 | 对外输出 / 权威维护对象 | 明确边界 |
|---|---|---|---|
| RCA | 接收企业目标；组织访谈、需求编译、计划和交付管理 | 需求基线、验收条件、计划、变更、交付清单 | 管理项目业务进度；项目 ID、成员和租户归属由公共项目模块维护 |
| DOA | 接收需求、数据授权和 TSA 的数据要求 | 本体、映射、数据质量、数据包登记 | 企业事实仍由企业数据服务或原系统维护；平台主要保存引用 |
| TSA | 接收需求、数据条件与资源信息；选择、构建、集成 | 技术方案、配置包、构建记录、候选版本 | 不自行改需求或企业事实；整改产生新候选版本 |
| DSHEval | 接收被测对象、评测配置和获准数据 | 测试定义、标签标准、运行、评分、All Trace、报告 | 产生评测事实；不替企业批准上线 |
| EVA | 对照需求和验收条件检查候选版本与评测证据 | 覆盖矩阵、评审、限制、整改与复评记录 | 引用 DSHEval 结果，不修改分数；不重复维护评测执行引擎 |
| LGA | 接收已发布版本、操作资料和角色权限 | 指导内容、培训记录、反馈 | 内容绑定发布版本；反馈回 RCA/TSA，不直接修改生产配置 |
| 企业业务 Agent | 接收业务任务、配置、数据和授权 | 结果、依据、待批准动作、外部执行回执 | 通过受控工具或业务接口操作，不直接持有跨模块改表权限 |
| DSH 运行底座 | 承载 Agent、模型和工具执行 | 会话、调用结果、可用运行事件 | 复用已验证能力；Studio 不再复制一套 Agent 执行器 |
| 公共模块 | 身份、项目、任务、文件、批准、发布的基础能力 | 对应公共主档与系统事实 | 是权威写入入口；可先作为同一后端的内部模块 |

RCA 组织交付，不等于拥有批准或发布权限。审批模块记录有权人员的真实决定；发布模块执行最终检查。企业项目是业务范围，不另设一个与公共项目主档并列的数据维护方。

### 2.2 一条主链路

```text
企业 / 项目身份
  → RCA：需求与验收基线
  → DOA：数据包；TSA：技术方案与构建（可交叉迭代）
  → TSA：固定候选版本
  → DSHEval：评测报告与证据
  → EVA：需求覆盖、限制、整改 / 就绪结论
  → 企业有权人员：批准指定对象及动作
  → 发布模块：重新核验并发布
  → 业务 Agent 运行；LGA 指导和收集反馈
  → RCA 变更管理 → 新候选版本
```

模块可以并行开发。交接时通过状态表达缺少的数据或能力，不用模块互相“等全部做完”。企业差异通过数据、本体、流程配置和连接器表达；只有真正需要不同算法或执行逻辑时才增加扩展代码，避免每家企业维护一个主干分支。

## 3. 公共字段与标识（拟定）

### 3.1 命名、类型和版本

| 项目 | 统一约定 | 说明 |
|---|---|---|
| 对外 JSON 字段 | camelCase | 与现有 DSHEval 主体格式一致 |
| 数据库字段 | 可采用 snake_case | 由映射层转换，不要求数据库和 JSON 同名 |
| 现有协议 | 保留原字段与枚举，适配转换 | 不批量改写已有 Planner、题库、第三方协议或历史结果 |
| 状态 | Studio 新接口用 UPPER_SNAKE_CASE | 既有小写状态由适配器映射 |
| 新对象 ID | 默认使用 UUID；按完整字符串处理 | 已有 ID 不重编号；通过显式映射关联，资产 ID 允许保留版本后缀 |
| 时间点 | UTC ISO 8601 | 例如 `2026-09-12T08:30:00.000Z`；业务日期另用 `YYYY-MM-DD` |
| 时长与容量 | 名称标明单位 | `timeoutMs`、`durationMs`、`byteLength` |
| 金额 | 十进制字符串 + 币种；持久化用精确数值表示 | 如 `{"amount":"123.45","currency":"CNY"}`；精度与舍入由业务字段定义 |
| 测量值 | 值、单位及必要精度 | DOA 定义标准单位与源单位转换，不由模型猜测 |
| 空值 | 缺省、null、空集合、0 各有含义 | DSHEval 未评分为 null，0 是真实分数 |
| 编码 | UTF-8、LF；交换使用 JSON，事件可用 JSONL | 不解析 HTML 或自然语言日志取得业务状态 |
| `schema` | 结构及协议版本 | Studio 新协议如 `dshstudio.task/v1`，不冒用 DSHEval schema |
| `version` | 业务对象内容版本 | 固定版对象不能原地改变内容 |
| `revision` | 可变记录的并发版本，非负整数 | 更新提交 `expectedRevision`，冲突返回 CONFLICT |
| `producerVersion` | 生成记录的软件版本 | 与模型、内容版本分开 |
| `contentDigest` | 内容摘要 | `{algorithm:"sha256",value,byteLength}`；value 为 64 位小写十六进制 |

文件摘要按原始字节计算；结构化对象摘要需固定规范化算法及排除字段。接入 DSHEval 时复用其记录对应的摘要函数，不用任意 JSON 序列化结果替代。Studio 的摘要构造函数和跨语言测试样例属于首期公共契约交付物。

### 3.2 作用域与基础引用

以下定义适用于 Studio 对外对象，不要求所有数据库表机械增加全部字段。

| 字段 | 类型与必填条件 | 语义 |
|---|---|---|
| `accessScope.kind` | `TENANT` 或 `PUBLIC`，必填 | 对象属于企业还是公共范围 |
| `accessScope.tenantId` | TENANT 时必填字符串；PUBLIC 时禁止 | 企业身份由服务端验证，不能相信客户端自报值 |
| `accessScope.projectId` | 项目对象必填；企业级对象可省略；PUBLIC 禁止 | 项目必须属于对应企业 |
| `createdAt` | 持久化对象必填时间点 | 由服务端生成 |
| `createdBy` | 需要记录创建身份时提供 `{kind,id}` | kind 为 USER 或 SERVICE；从已认证身份取得 |
| `updatedAt`、`revision` | 可变业务记录提供 | 不为不可变证据伪造更新过程 |
| `correlationId` | 跨模块任务请求必填字符串 | Studio 调用链标识；不占用 DSHEval 的 traceId |
| `requestId` | 每次请求由入口生成 | 排查一次请求；不同于业务幂等键 |
| `idempotencyKey` | 创建任务和执行有副作用命令时必填 | 在企业、调用身份与操作范围内去重 |

Studio 的 `accessScope` 表达访问权限；DSHEval 的 `scope` / `ScopeRef` 表达 target/run/case/attempt 等执行归属，二者不能互相替代。公共对象也需写入和发布权限，PUBLIC 不等于所有人可修改。

拟定的 `ObjectRef`：`{objectType, objectId}`。用于冻结输入、评测、评审、批准和发布的 `FrozenRef` 进一步要求 `version` 与 `contentDigest`。跨范围引用由读取方授权校验；ID 可见不代表内容可读。这里的 Studio Ref 与 DSHEval 现有 `Ref<T>` 是不同协议，由适配层转换。原生对象没有独立业务版本时，适配器可以采用内容摘要作为明确的版本令牌，并注明规则；不伪造一个底层并不存在的发布版本。

### 3.3 任务与评测 ID 映射

| 名称 | 统一含义 |
|---|---|
| `taskId` | Studio 逻辑任务，失败重试仍可属于同一任务 |
| `attemptId` | Studio 一次实际执行尝试；重试生成新 ID |
| `evaluationRunId` | Studio 指向 DSHEval 一次评测运行的字段，映射 DSHEval 原生 `runId` |
| DSHEval `scope.caseId` / `scope.attemptId` | 该评测内部的题目执行实例和尝试，不与 Studio attemptId 共用语义 |
| `sourceCaseId` | 新接口需要引用题目定义时采用的字段；与运行实例分开 |
| `sessionId` | 运行底座会话；可有多个，由适配器关联 |
| `traceId` | DSHEval 一份 All Trace 的 ID，不能当成 Studio correlationId |

**调整原稿：** 不再用一个通用 `run_id` 同时表达模块尝试和评测运行。首次接入建立持久化映射，不通过拆目录名推断关系。

## 4. 最小可联调契约（拟定）

### 4.1 先实现这些边界

下表是待落地的接口定义范围，不预设 HTTP 路径或消息中间件。内部模块可以直接调用；跨进程再提供相同语义的 API。

| 操作 / 对象 | 最少输入 | 最少输出与规则 |
|---|---|---|
| 项目查询与授权 | 认证上下文、projectId、action | 核验后的企业/项目上下文；越权明确拒绝 |
| 创建任务 | taskType、协议版本、accessScope、ownerModule、inputRefs、完成条件引用、deadlineAt（可选）、幂等键 | taskId、PENDING、revision；输入固定，重复相同请求返回同一任务 |
| 接收任务 | taskId、expectedRevision、接收者 | ACCEPTED 或 REJECTED、reasonCode、责任归属；接收成功才进入可执行队列 |
| 查询 / 取消 / 重试 | taskId、权限；修改带 expectedRevision | 状态、attempts、未解决项、最新结果引用 |
| 完成尝试 | taskId、attemptId、执行令牌、结果、证据引用 | 条件验证后的状态更新；旧工作进程不能覆盖新尝试 |
| 登记数据包 / 配置包 / 候选版本 | 版本清单、摘要、作用域、依赖引用 | FrozenRef；拒绝同版本不同内容 |
| 提交 / 查询评测 | 候选引用、评测配置引用、任务关联、授权 | evaluationRunId、运行状态、受控报告引用；幂等与关联持久化 |
| 获取文件 / 报告 | 对象引用、认证上下文 | 经授权的数据或短期访问方式；不把永久公开 URL 当作文件 ID |
| 评审 | 需求基线、候选、报告、验收条件引用 | READY / CHANGES_REQUIRED / INSUFFICIENT_EVIDENCE，覆盖和限制 |
| 批准 / 撤销 | 对象版本、动作范围、条件；真人认证操作 | 批准记录；Agent 可发起申请，不能创建真人批准事实 |
| 发布 | 候选、评审、批准引用、部署目标、expectedRevision | 发布记录或拒绝原因；执行前重新核验权威记录 |

任务结果至少包含 `taskId`、`attemptId`、`status`、`outputRefs`、`evidenceRefs`、`unresolvedItems`；有错误时提供 `error`。完整证据可以是一份结果引用，不要求把所有内容内嵌到任务记录。

交接发起方提交输入版本、完成条件、未解决项和预期接收方；接收方返回接受或拒绝回执。拒绝不能被解释为已开始运行。完成条件可以来自版本化任务类型定义，避免每次写一套自然语言验收规则。

### 4.2 任务状态与异常

Studio 任务的主要状态为：

| 状态 | 进入条件 | 后续转换 |
|---|---|---|
| PENDING | 任务已创建并指派，等待接收方回执 | 接受后 QUEUED；拒收后 BLOCKED；可取消 |
| QUEUED | 接收完成、输入固定，等待执行 | RUNNING；取消后 CANCELLED |
| RUNNING | 接收方成功领取任务并建立 attempt | SUCCEEDED / FAILED / WAITING_APPROVAL / BLOCKED / CANCEL_REQUESTED |
| WAITING_APPROVAL | 有明确批准申请和等待原因 | 有效批准后 QUEUED；拒绝后 FAILED 或 CANCELLED，写明原因 |
| BLOCKED | 拒收、缺输入、依赖不可用或外部结果待核实 | 已接受任务解除条件后 QUEUED；重新分派则 PENDING；可取消 |
| CANCEL_REQUESTED | 已发出取消，但运行尚未确认停止 | 确认停止后 CANCELLED；已完成则记录真实终态及取消未生效原因 |
| SUCCEEDED | 本任务完成条件满足，结果已保存 | 终态；新增需求创建新任务 |
| FAILED | 本次执行失败且没有运行中的尝试 | 符合重试策略时建立新 attempt 后回 QUEUED |
| CANCELLED | 确认不再执行，保留已发生外部动作 | 终态；恢复业务须显式创建新任务 |

任务另存最近一次交接回执（ACCEPTED / REJECTED、接收方、时间、原因），避免仅凭运行状态猜测是否接收。条件补齐但输入内容发生变化时，创建新任务并关联前序任务，重新接收；不得改写已有尝试使用的输入。

领取、状态变更和结果提交通过事务及 revision/执行令牌校验。服务重启后核查过期领取记录及底座执行情况，不直接把所有 RUNNING 重跑。

同一 attempt 内的等待恢复，只有底座支持可靠恢复且输入未变才采用；否则生成新 attempt，并保留前序关系。截止时间到达不等于外部进程已经停止。

`SUCCEEDED` 表示本任务完成。例如评测任务成功完成后，Agent 仍可能得低分；项目能否验收由 EVA 与企业批准另行判断。

错误采用 `{code, message, retryable, detailRef?}`，首期共享类别为 INVALID_INPUT、UNAUTHORIZED、FORBIDDEN、NOT_FOUND、CONFLICT、UNSUPPORTED、DEPENDENCY_UNAVAILABLE、TIMEOUT、EXECUTION_ERROR。专业 reasonCode 在模块内维护。DSHEval 原生 Failure 结构保留，由适配层输出 Studio 错误，不直接替换底层记录。

### 4.3 幂等、未知结果与人工接管

- 同一作用域的同一幂等键、相同输入返回原结果；相同键配不同输入返回 CONFLICT。
- 对下单、发通知等外部动作，调用前记录操作 ID、请求摘要和授权；回执关联同一操作。
- 超时后结果不明，记录外部动作结果 UNKNOWN，任务进入 BLOCKED；先查询或对账，不能盲目重试。
- 人工接管记录接管人、原因、外部实际结果、后续决定和依据；只允许有权限的接口更新。
- 取消任务或回滚软件不会自动撤销订单等业务事实；补偿动作也需自己的权限、幂等键和回执。
- 重试需限制次数和时间；成本上限仅在确有预算要求的任务上配置，不作为所有接口的必填字段。

## 5. 数据包、候选版本与发布闭环

### 5.1 统一包清单，保留异构内容

数据包、配置包不一定是 ZIP 文件，可以是版本清单加受控文件或查询引用。

| 对象 | 最少需要固定的内容 | 维护方 |
|---|---|---|
| 数据包 | ID、版本、accessScope、本体引用、来源、快照或查询方式、更新时间/时效、质量说明、授权引用、内容摘要 | DOA |
| 配置包 | ID、版本、Agent/插件/工具绑定、流程和规则、数据引用、权限策略引用、异常策略、摘要 | TSA |
| 候选版本 CandidateManifest | 需求和验收基线、代码构建、提示词、插件/工具依赖、配置、数据包、模型与参数、环境配置 | TSA |
| 评测绑定 EvaluationBinding | Studio task/attempt、候选摘要、DSHEval target/snapshot、runId、测试与标签版本、报告引用 | DSHEval 适配模块 |
| 评审 Review | 同一候选摘要、需求与验收基线、报告引用、覆盖、限制、结论 | EVA |
| 批准 Approval | 批准人、对象及摘要、动作、范围、条件、有效期、决定及撤销状态 | 批准模块 |
| 发布 ReleaseRecord | 同一候选摘要、评审/批准引用、环境、部署结果、实际部署摘要、检查结果、前一发布引用 | 发布模块 |
| 培训与指导 | 内容版本、适用发布 ID、角色和可用功能 | LGA |

每个依赖引用都需可解析并检查版本；机器路径不能成为包唯一定位方式。密钥仅保存安全引用。依赖不兼容或引用失效时明确阻塞，不自动换到“最新版本”。

### 5.2 消除版本循环依赖

**候选版本先固定，后续记录引用它。** 候选清单不把未来报告、批准记录包含进自身摘要，否则报告引用候选、候选又包含报告，会形成循环。

```text
CandidateManifest（固定摘要）
  ├── EvaluationBinding → DSHEval 报告
  ├── EVA Review → 对应报告与候选摘要
  ├── Approval → 对应候选摘要、评审和获准动作
  └── ReleaseRecord → 上述记录及实际部署对象
```

需要导出“完整交付包”时，再生成一份索引，汇集以上记录；导出索引不是新的被测候选。

批准仅对被绑定的版本和动作有效。发布前检查：候选摘要一致、评审仍有效、批准未过期/撤销、权限及环境条件满足。用事务或版本条件防止检查后指针被换成另一个候选；多步骤部署在关键外部动作前再次核验并记录时间。

候选代码、提示词、插件、配置或固定数据变化产生新版本。可以做受影响测试加必要回归；复用旧证据需说明为什么仍适用，并形成新的评审，不直接沿用旧批准。

### 5.3 动态数据不能只记查询时间

| 数据方式 | 此次运行保留什么 | 可复现性 |
|---|---|---|
| 固定快照 | 数据包版本、源版本、文件或对象摘要 | 数据和环境可取回时可重放 |
| 支持历史查询的源 | 源标识、查询参数摘要、as-of/快照标识、返回摘要 | 需确认源保留期限和权限 |
| 不支持历史查询的源 | 授权允许的返回快照，或最小必要内容和来源凭据 | 仅有时间戳不足以复现；无法保留内容时明确限制 |

记录“用了哪个查询”不足以证明“当时看到了哪些结果”。不能留存完整内容时，保存获准的摘要、版本和来源说明，并标记证据只能追溯、不能完整重放。

业务 Agent 按批准策略读取更新数据时，不必每条业务事实更新都重新批准软件发布；但需记录当次实际输入。超出批准的数据范围、时效或质量条件时，阻塞动作或进入变更流程。

## 6. DSHEval 接入与评价边界

### 6.1 保留现有证据和 Judge 设计

已核对的当前接口：

| 对象 | 现有协议与语义 |
|---|---|
| All Trace | `dsheval.all-trace/v1`；entries、sources、coverage、artifacts、integrity、scope、摘要 |
| 三层证据 | AGENT：Agent 内部记录；ENVIRONMENT：外部观测；DELIVERY：回答与文件 |
| Judge 输入 | `{label, case, allTrace}`；每个标签读取同一份三层证据 |
| 标签 | `dsheval.label/v2`；评分标准和 Judge 配置，资产 ID 可仍为 `label.xxx/v1` |
| LabelScore | `dsheval.label-score/v1`；label/case/allTrace 摘要、分数、理由、证据 ID、模型 |
| 标签状态 | SCORED 有数值；UNASSESSABLE 和 ERROR 的 score 为 null |
| 汇总 | 保留 scoredCases、unassessableCases、errorCases；不把无法判断折算成 0 |
| 报告 | `dsheval.result/v1` 的结构化结果；HTML 是展示视图 |

静态插件清单是 Planner 的输入，不是能力评分。不同 Agent 可选不同评测集；EVA 比较结果时须核对维度、样本、题型、评分规则和未覆盖范围。需要可比排名时，应另外设计共同任务或校准方法。

All Trace 的完整性标记描述采集情况，不预先替 Judge 决定分数。Agent 声称成功、Observer 看到变化、原生 Benchmark 检查通过，是不同证据；不能互相冒充。

保留异构题目的原始语义和评分材料。统一接入外壳不等于所有数据集环境、工具与原生检查器已经适配。渐进式证据获取仍属于后续优化，本文不新增旧式 EvidenceContract / Closure / Gate。

### 6.2 Studio 需要增加的薄适配层

| 工作 | 首期做法 |
|---|---|
| 关联企业与项目 | EvaluationBinding 保存 accessScope；不要假定 DSHEval ScopeRef 已有 tenantId/projectId |
| 关联候选版本 | 显式保存候选摘要与 targetSnapshot 的映射；验证真正启动的是该候选 |
| 防止重复提交 | 持久化 task/attempt → evaluationRunId 映射；恢复时查询已存在运行 |
| 获取结果 | 读取并验证结构化报告；只在 Studio 保存摘要与受控引用 |
| 权限 | 报告、原始 trace、附件、导出都经过授权；不能只保护平台页面 |
| 原生存储兼容 | 保留当前文件产物与内容摘要；先增加索引和访问接口 |
| 原生能力缺口 | 如果提交后无法查询是否已运行，标为结果待核实，不能靠重新提交“恢复” |

**适配请求片段示例：** 以下用于说明命名，不是当前 DSHEval 原生输入，也不是完整任务请求。

```json
{
  "accessScope": {
    "kind": "TENANT",
    "tenantId": "tenant-demo",
    "projectId": "project-demo"
  },
  "taskId": "task-demo",
  "attemptId": "attempt-demo",
  "correlationId": "corr-demo",
  "evaluationRunId": "e2e-demo",
  "nativeScope": {
    "targetId": "target-demo",
    "runId": "e2e-demo",

```

示例 ID 为说明用标识，保留原生 ID 映射，不代表新建 Studio ID 的生成规则。

### 6.3 DSH 能力复用核对

| 能力 | 当前证据范围 | 实施决策 |
|---|---|---|
| DSH 执行与输入交付 | DSHEval 已有对应接入代码；本次未审计 DSH 内核 | 复用现有接入，验证会话和候选绑定 |
| Agent Trace / Observer / Judge | 已核对 DSHEval 当前类型 | 复用，补 Studio 身份与版本关联 |
| 企业授权、动作批准、发布原子检查 | 两份草案描述了要求；没有本次实现证明 | 由平台与 DSH 负责人逐项确认复用点和缺口 |
| 取消、查询、恢复、业务幂等 | 不能由“DSH 可运行”推导已支持 | 以真实故障联调确认；不支持处采用显式阻塞与人工核实 |
| 数字人、记忆、多模型治理 | 尚未核对 | 首期仅保留所需调用记录与权限边界，不先建统一平台 |

## 7. 存储、访问与运行保障

### 7.1 推荐起步布局

先统一逻辑归属与受控接口，物理拆分根据负载和部署要求决定。

| 数据域 | 首期建议 | 权威维护及拆分条件 |
|---|---|---|
| 平台业务 | 一个模块化业务后端；能满足要求的既有关系型存储优先复用 | 企业/项目主档、需求、任务、包登记、评审批准和发布；不要求每个 Agent 一个数据库 |
| DSHEval | 保留现有结果文件；平台保存受控索引和关联 | DSHEval 维护完整评测；查询量、写入量或并发需求实测后再决定是否增加独立评测数据库 |
| 企业数据 | 原系统保留权威事实；确需保存的数据按企业作用域存储 | 授权允许且隔离验收通过，可共享存储；独立恢复、凭据或部署需要时分逻辑库 |
| 文件 / 证据 | 一个文件访问模块；首期可使用受控文件目录 | 记录摘要、权限、版本；多节点或容量需求出现时迁往对象存储 |
| 企业专属环境 | 按合同和实际访问边界部署 | 网络、资源、恢复要求无法由共享环境满足时独立实例或环境 |

数据库产品与版本暂不强行指定。先盘点现有产品、事务能力、并发控制、维护经验和部署约束；选一套默认基线。已有可用模块通过适配保留，迁移收益明确后再迁。

独立逻辑库不会隔离共享实例的 CPU、内存和 I/O；Schema 或表名前缀不会自动实现企业隔离。公共生态评测与企业私有评测应独立授权；当共享执行环境无法证明私有资料隔离时，首期使用分开的工作目录、身份和必要的运行环境。

### 7.2 数据位置与唯一写入方

| 对象 | 逻辑位置 | 唯一写入入口 |
|---|---|---|
| tenant / project / member | 平台 core | 公共身份与项目模块 |
| 需求、验收基线、项目业务计划 | 平台 rca | RCA 模块 |
| 本体、企业映射、事实 | 企业数据域或既有系统 | DOA 管理的企业数据服务 / 原系统 |
| 数据包清单与质量、来源引用 | 平台 doa；私有实体留企业数据域 | DOA 模块 |
| 配置、构建、候选清单 | 平台 tsa | TSA 模块 |
| 任务、尝试、交接、待发消息 | 平台 workflow | 公共任务模块；RCA 等发命令 |
| 评测定义、运行、完整证据 | DSHEval 原生存储 | DSHEval |
| 评测与候选、项目的关联 | 平台 evaluation-binding | DSHEval 适配模块 |
| 评审、限制、整改 | 平台 eva | EVA 模块 |
| 批准、发布、文件登记 | 平台对应公共区域 | 对应公共模块 |
| 指导内容与反馈 | 平台 lga | LGA 模块 |

这些是逻辑区域，不要求真实数据库必须支持同名 Schema。Agent 使用受控接口；模块化后端通过代码依赖边界限制写入，跨进程模块使用受限账号。迁移账号与运行账号分开，不把 DBA 权限交给 Agent。

### 7.3 企业隔离的具体检查点

| 位置 | 首期要求 |
|---|---|
| 请求入口 | 从认证身份解析企业成员和项目权限；客户端字段只用于请求目标，不能授予权限 |
| 数据查询与关联 | 私有查询带 tenantId；关联校验双方企业及项目范围；业务唯一键含企业作用域 |
| 后台任务 | 持久化服务身份和 accessScope；执行时核验授权是否仍有效 |
| 文件、报告、导出 | 每次获取和导出均授权；不裸露目录或永久公开地址 |
| 缓存、检索、会话 | key 和检索范围包含企业及必要项目权限；角色切换不扩大范围 |
| 连接池 | 每次使用前设置、归还时清理上下文；异常路径同样测试 |
| DSHEval 私有材料 | 题目参考答案、Judge 上下文和企业证据不混入 Agent 公开输入；目录名不等于访问控制 |

不要求首期开发通用“任意字段权限引擎”。先对已有敏感接口按角色返回明确视图，保证实际用到的限制可执行。

### 7.4 一致性与事件

同进程、同数据库的必要业务更新优先使用本地事务，不为了统一而把每个动作都做成事件。

跨进程异步交接时，业务更新和待发送消息在本地同一次提交中记录；后台发送，消费方按 eventId 去重，并将接收记录与本地状态更新一起提交。初期可用数据库待发/已收表与轮询任务，不必先引入消息集群。

最小事件字段：`schema`、`eventId`、`eventType`、`accessScope`、`subjectRef`、`subjectRevision`、`occurredAt`、`correlationId`、`payload`。事件载荷只放必要信息，不广播企业原始内容。

按至少一次投递处理重复；用对象 revision 识别旧事件，发现缺口则查询权威状态。记录失败和重试，超过策略边界进入人工处理。关键关口重新读取权威评测、批准及候选记录，不能只相信缓存状态。

跨库无普通外键时，保存受控引用并做提交时检查与定期对账。首期对账覆盖任务结果、候选—报告绑定、文件可取回、消息积压；不建设全量分布式事务。

### 7.5 迁移、备份与恢复

- 结构变更通过版本化迁移脚本；先扩展兼容，再迁移和切换，确认后删除旧字段。
- 历史 ID 建映射，重复主档人工确认合并；不重写原始评测证据来迎合新命名。
- 每个企业部署记录应用与数据库结构版本。数据库回滚不保证数据变更可逆，迁移前明确恢复或向前修复方式。
- 备份至少能对应数据库、文件版本清单、权限和必要配置；密钥恢复渠道单独管理，不能把密钥明文打包。
- 上线前约定可接受的数据丢失窗口与恢复时限，并在隔离环境恢复一次完整项目。
- 共享库单企业恢复先在隔离环境取回，再定向校验导入；不能整库回退覆盖其他企业新数据。
- 恢复后暂停副作用任务，核对已发生的订单、通知和外部回执，确认后恢复调度。

归档、删除覆盖文件、缓存、索引和导出副本。保留期限由项目确定；备份副本按保留周期处理。恢复时重新应用删除/撤权记录，避免已删除资料重新对外可见。

## 8. 开发方式与实施顺序

### 8.1 每个模块最少交付什么

一个 README、可启动项目、对外契约及样例、必要测试、配置示例和已知限制即可。不要要求每个模块单独写 22 份规范。

共享契约建议集中在一个版本化目录或小包，存放公共类型/Schema、错误码、状态、摘要与 ID 映射样例。TypeScript 与 Python 可以使用各自工具，至少消费同一套 JSON 样例验证。

首期契约需补齐：必填条件、枚举、最大输入范围、未知字段策略、兼容规则和失败样例。新增必填字段、改含义或单位要升版本并通知消费者；新增可选字段也先验证旧消费者是否接受。

运行数据、依赖、构建目录和真实密钥不提交 Git。修改共享接口时同时检查生产者与消费者；PR 说明目的、影响、验证和限制。文档修改只做内容与链接检查，不堆无关测试。

### 8.2 建设顺序与成本

优先级：**P0 是相关能力对真实企业开放前的可靠性底线；P1 是首个完整项目闭环必须补齐；P2 是复用验证后完善。** 不使用某项能力时无需提前造平台，例如首期只有文字交互便不开发数字人能力。

成本标记用于比较工作量：低＝单模块配置或薄封装；中＝多个模块联调；高＝新基础设施或存量迁移。不是工期承诺；完成盘点后再由负责人估算。

| 顺序 | 要做什么 | 优先级 / 相对成本 | 完成标志 / 负责人 |
|---|---|---|---|
| 0 | 盘点各模块存储、接口、DSH 能力与首个项目依赖；确定负责人和真实验收任务 | P1 / 低至中 | 有现状与缺口清单；平台牵头、各模块确认 |
| 1 | 固定公共 ID、accessScope、Ref、任务状态和错误；建立样例契约 | P1 / 中 | 两个模块能交换可校验数据；平台与模块共同完成 |
| 2 | 落实身份、企业隔离、受控文件和私有评测访问 | P0 / 中 | A/B 企业越权测试通过；平台、DSHEval |
| 3 | 任务领取、持久化、幂等、未知结果处理；有异步交接时增加待发/已收记录 | P0 / 中 | 重启、重复请求和超时不导致重复副作用；平台、执行方 |
| 4 | 串起 RCA→DOA→TSA→DSHEval→EVA；加候选及报告映射 | P1；版本准确性 P0 / 中 | 一个候选可追溯到需求、数据与真实评测；各模块 |
| 5 | 批准、发布检查、恢复演练及版本化指导 | P0（发布与恢复）；P1（指导）/ 中 | 变版本后旧批准不能发布；隔离恢复可用；平台、EVA、LGA |
| 6 | 用第二个企业场景复用；归纳真正的扩展点 | P1 / 中 | 无企业专属主干分支，差异主要在配置、数据、连接器 |
| 后续 | 查询优化、独立评测 DB、资源隔离、资源市场、数字人、复杂成本统计 | P2 / 中至高 | 根据负载、场景和收益逐项立项 |

这套首期建设无需新增多个独立服务、消息集群或统一模型网关。若现有系统已有满足要求的能力，直接复用并补契约测试。

### 8.3 两个场景的联调验收

以下是建议验收路径，不是对汇甬或采购项目已有业务规则的认定；具体任务、阈值和授权由项目负责人确认。

| 环节 | 汇甬售前示例 | 采购供应链示例 | 共用验证点 |
|---|---|---|---|
| 需求 | 设备选型/方案建议，参数和人工确认范围 | 供应商比较/采购建议，预算和批准范围 | 同一项目 ID；需求与验收基线有版本 |
| 数据 | 含水率、处理量、设备参数及来源 | 供应商、价格、交期及来源 | 单位、时效、来源、质量及授权可追溯 |
| 构建 | 选型配置和所需工具 | 比价配置和采购系统连接器 | 候选固定；依赖和数据引用可解析 |
| 评测 | 参数依据、任务结果、证据支持 | 计算、供应商条件、业务边界 | DSHEval 记录真实任务和证据；无法评价如实保留 |
| 评审与批准 | 核对覆盖后批准指定版本/动作 | 核对覆盖后批准指定版本/动作 | EVA 就绪不等于企业批准 |
| 运行 | 生成方案；对外发送按授权执行 | 先演示建议；真实下单仅在获准时执行 | 动态数据使用记录、幂等与回执 |
| 指导与反馈 | 使用步骤和缺参数反馈 | 采购流程指导与异常反馈 | 对应发布版本，变更回 RCA |

两个场景都应加入：缺数据、批准过期、候选被修改、消息重复、外部结果未知、后台任务越权、报告下载越权、恢复后副作用防重放。首个场景验证闭环，第二个验证复用；不同业务内容无需强行共用一张事实表。

## 10. 采用本基线前需落实的决定

| 待决定事项 | 建议默认方向 | 确认依据 |
|---|---|---|
| 首个企业场景与真实完成条件 | 两个场景中选依赖更明确的先做，另一个验证复用 | 项目负责人确认输入、外部动作与授权 |
| 公共契约维护人 | 一名平台负责人牵头，各模块维护专业字段 | 明确到人，避免多人同时改公共定义 |
| 数据库和文件技术基线 | 先复用能满足首期要求的现有设施 | 存量盘点、隔离能力和维护成本 |
| DSH 可复用能力 | 按 §6.3 逐项实测 | 代码入口与真实调用回执 |
| 多租户或企业独立部署 | 以实际授权及可验证隔离为准 | 不能证明隔离时，不把真实私有数据接入共享路径 |
| 批准动作与有效条件 | 由企业有权人员和产品明确，程序执行 | 哪些动作需要批准、版本变化如何处理 |
| 恢复与保留目标 | 对首个项目给出具体值 | 业务可接受损失、恢复时限、数据授权范围 |

这些决定可以通过一次短评审记录落定。文档确认后，优先交付可运行的契约样例与一个完整场景；以联调结果修订规范。
